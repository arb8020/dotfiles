1. The Spectrum

Every eval harness sits somewhere on a spectrum from "just a script" to "hosted product with dashboards." The choices that matter:

Script Product
Decision Script end Product end
Config format Python code (simple-evals) YAML/JSON + REST API (OpenAI)
Eval definition class Eval: def __call__ Declarative spec + scorer registry
Run submission eval_obj(sampler) POST /v1/evals/{id}/runs
Results JSON files on disk Dashboard + experiment diffs
Run tracking Timestamp in filename SQLite/Postgres registry
Granularity Maximum — you control everything Minimum — the platform decides
Casey's granularity principle applies here: never supply a higher-level function that can't be trivially replaced by a few lower-level functions that do the same thing. The product layers should be on top of the script layers, not replacements. Braintrust gets this right. OpenAI's hosted API got it wrong (no escape hatch to local).

2. OpenAI simple-evals

simplest research

67 lines of types. No config files, no registry, no CLI. The entire API surface:

# /tmp/simple-evals/types.py — the ENTIRE type system

@dataclass
class SamplerResponse:
    response_text: str
    actual_queried_message_list: MessageList
    response_metadata: dict[str, Any]

class SamplerBase:
    def __call__(self, message_list: MessageList) -> SamplerResponse: ...

@dataclass
class SingleEvalResult:
    score: float | None
    metrics: dict[str, float] = field(default_factory=dict)
    html: str | None = None
    convo: MessageList | None = None

@dataclass
class EvalResult:
    score: float | None
    metrics: dict[str, float] | None
    htmls: list[str]
    convos: list[MessageList]

class Eval:
    def __call__(self, sampler: SamplerBase) -> EvalResult: ...

# Usage — that's it. Instantiate and call.

sampler = ChatCompletionSampler(model="gpt-5.5")
result = MathEval(num_examples=100)(sampler)
# result.score -> 0.87, result.metrics -> {"exact_match": 0.87}
# Written to /tmp/math_gpt-5.5_20260612.json

What's good

  • Impossible to misunderstand. The entire contract is Eval(sampler) → EvalResult.
  • Maximum granularity — you can do anything inside your Eval class.
  • No framework lock-in. It's just dataclasses.

What's missing

  • No run tracking. Results are loose files with timestamps.
  • No concurrency control. Each eval manages its own parallelism.
  • No config/code separation. Can't submit a run without modifying Python.

3. Eleuther lm-evaluation-harness

research declarative

YAML-driven. The most widely used harness for open model benchmarking (leaderboard standard).

# lm_eval/tasks/gsm8k/gsm8k.yaml — a complete task definition

task: gsm8k
dataset_path: openai/gsm8k
dataset_name: main
output_type: generate_until
training_split: train
test_split: test
num_fewshot: 5

doc_to_text: "Question: {{question}}\nAnswer:"
doc_to_target: "{{answer}}"

metric_list:
  - metric: exact_match
    aggregation: mean
    higher_is_better: true
    regexes_to_ignore:
      - ","
      - "\\$"
      - "(?s).*#### "

generation_kwargs:
  until: ["Question:", "</s>"]
  temperature: 0.0

filter_list:
  - name: "strict-match"
    filter:
      - function: "regex"
        regex_pattern: "#### (\\-?[0-9\\.\\,]+)"
      - function: "take_first"

# Python entry point

from lm_eval.evaluator import simple_evaluate

results = simple_evaluate(
    model="vllm",
    model_args="pretrained=meta-llama/Llama-4-8B",
    tasks=["gsm8k", "mmlu"],
    num_fewshot=5,
    batch_size="auto",
    limit=100,            # cap samples for dev
    log_samples=True,
)
# results["results"]["gsm8k"]["exact_match,strict-match"] → 0.73

# Results schema (TypedDict)

EvalResults = {
    "results":          dict[str, TaskMetrics],    # per-task scores
    "configs":          dict[str, dict],           # resolved YAML
    "versions":         dict[str, str | float],
    "n-shot":           dict[str, int],
    "higher_is_better": dict[str, dict[str, bool]],
    "samples":          dict[str, list[SampleResult]],
    "model_name":       str,
}

What's good

  • Declarative tasks. YAML is readable by non-engineers and diffable by git.
  • Template strings ({{question}}) keep formatting separate from logic.
  • Filter chains for answer extraction — composable post-processing.
  • Standardized metrics. Everyone compares on the same definitions.

What's missing

  • No agent support. It's prompt-in/text-out. Can't eval tool-using agents.
  • No sandbox/workspace concept. Tasks run in the harness process.
  • YAML configs get complex fast — !function tags, template inheritance.

4. OpenAI evals (archived)

research

Pioneered the registry pattern: YAML files map eval names to Python classes. Now archived, but the patterns influenced everyone after it.

# evals/registry/evals/language.yaml

hellaswag:
  id: hellaswag.val.ab-v1
  metrics: [accuracy]

hellaswag.val.ab-v1:
  class: evals.elsuite.multiple_choice:MultipleChoice
  args:
    dataset: hf://hellaswag?split=validation
    instructions: "Choose the most plausible continuation."

# Run spec — auto-generated, not user-written

@dataclass
class RunSpec:
    completion_fns: list[str]
    eval_name: str
    base_eval: str
    split: str
    run_config: dict[str, Any]
    created_by: str
    run_id: str = None     # auto: timestamp + random
    created_at: str = None

# Event-based recording
@dataclass
class Event:
    run_id: str
    event_id: int
    sample_id: str | None
    type: str              # "match" | "sampling" | "metrics" | "error"
    data: dict
    created_by: str
    created_at: str

Key pattern: the registry

YAML maps names → classes. CLI resolves the name, instantiates the class, runs it. This is the eval_name → class + args indirection that lets you say oaieval gpt-4 hellaswag without knowing Python.

The Event recorder is worth noting: every scoring decision, every sample, every error is an Event with a run_id. This is proto-wide-events. Obol already does this better with structured logging.

5. UK AISI Inspect

gov-backed framework

The most complete open-source eval framework. Composable solver/scorer/metric pipeline. 200+ pre-built evals. The closest analog to what Obol could become.

# Task definition — decorator registers it

from inspect_ai import Task, task, eval
from inspect_ai.dataset import hf_dataset
from inspect_ai.scorer import model_graded_qa, accuracy, stderr
from inspect_ai.solver import chain_of_thought, generate, self_critique

@task
def my_eval():
    return Task(
        dataset=hf_dataset("openai/gsm8k", split="test"),
        solver=[
            chain_of_thought(),   # composable solver pipeline
            generate(),
            self_critique(),
        ],
        scorer=model_graded_qa(),
        metrics=[accuracy(), stderr()],
        sandbox="docker",         # tasks run in sandboxes
        epochs=3,
        message_limit=50,
        token_limit=100_000,
        time_limit=300,
    )

# CLI
$ inspect eval my_eval.py --model openai/gpt-5.5 --max-connections 10

# Programmatic
results: list[EvalLog] = await eval(
    "my_eval.py",
    model="openai/gpt-5.5",
    max_samples=64,
    max_connections=10,
    log_dir="./logs",
)

# View results
$ inspect view

# Task.__init__ signature — the full parameter space

Task(
    dataset:       Dataset | Sequence[Sample] | None,
    setup:         Solver | list[Solver] | None,       # pre-eval setup
    solver:        Solver | Agent | list[Solver],      # the agent/chain
    cleanup:       Callable | None,                    # post-eval teardown
    scorer:        Scorer | list[Scorer] | None,
    metrics:       list[Metric] | dict | None,
    model:         str | Model | None,
    config:        GenerateConfig,                     # temperature, max_tokens, etc
    sandbox:       SandboxEnvironmentType | None,      # docker, k8s, etc
    epochs:        int | Epochs | None,
    fail_on_error: bool | float | None,
    message_limit: int | None,
    token_limit:   int | None,
    time_limit:    int | None,
    cost_limit:    float | None,
    early_stopping: EarlyStopping | None,
    name:          str | None,
    version:       int | str,
    metadata:      dict[str, Any] | None,
    tags:          list[str] | None,
)

What's good

  • Solver composition. [chain_of_thought(), generate(), self_critique()] — the agent pipeline is explicit and reorderable.
  • Sandbox support (Docker, K8s) — tasks run in isolated environments.
  • Granularity. You can use the full Task, or just a scorer, or just a dataset. Layers don't force you.
  • Built-in viewer for results inspection.
  • Epochs + reducers for statistical rigor (pass@k, mean, mode).

What's worth noting

  • The Task constructor has ~20 parameters. It's at the edge of "too many knobs."
  • No experiment registry or run comparison built in — just log files.
  • The solver/scorer split maps well to Obol's runtime/verify split.

6. Braintrust

product

The most product-oriented. TypeScript-first, hosted experiment tracking with diffs. This is what "hosted evals as a product" looks like.

# The core API — one function call

import { Eval } from "braintrust";

Eval("my-eval", {
  data: () => [
    { input: "What is 2+2?", expected: "4" },
    { input: "Capital of France?", expected: "Paris" },
  ],

  task: async (input) => {
    const response = await openai.chat.completions.create({
      model: "gpt-5.5",
      messages: [{ role: "user", content: input }],
    });
    return response.choices[0].message.content;
  },

  scores: [Factuality, ExactMatch],

  experimentName: "baseline-v1",
  trialCount: 3,
  maxConcurrency: 10,
  metadata: { git_sha: "abc123" },
});

# The Evaluator interface (TypeScript generics)

interface Evaluator<Input, Output, Expected, Metadata, Parameters> {
  data:             EvalData<Input, Expected, Metadata>;
  task:             (input: Input, hooks: EvalHooks) => Promise<Output>;
  scores?:          EvalScorer<Input, Output, Expected, Metadata>[];
  experimentName?:  string;
  trialCount?:      number;
  maxConcurrency?:  number;
  metadata?:        Record<string, unknown>;
  tags?:            string[];
  timeout?:         number;
  baseExperimentName?: string;   # compare against this
}

# Score — same shape everywhere
type Score = {
  name: string;
  score: number | null;          # 0-1
  metadata?: Record<string, unknown>;
};

What's good

  • Experiment diffs. baseExperimentName gives you "what changed since last run" for free.
  • The Eval() function is the entire surface. Data, task, scores — three concerns, one call.
  • Hosted tracking. Results go to a dashboard automatically. No file management.
  • Score type is universal. {name, score, metadata} — every scorer returns the same shape.

What's worth noting

  • TypeScript-first is a real choice. Python SDK exists but feels like a port.
  • Tight coupling to hosted service. Hard to use fully offline.
  • The generics (Evaluator<Input, Output, Expected, Metadata, Parameters>) are complex.

7. Thinking Machines Tinker

training-first

Evals are a side feature of a training platform. The interesting pattern: evals bolt onto the training loop as inline evaluators.

# Standalone eval

from tinker_cookbook.eval.benchmarks import run_benchmarks, BenchmarkConfig

results = await run_benchmarks(
    ["gsm8k", "mmlu_pro", "ifeval", "mbpp", "math-500"],
    sampling_client,
    renderer,
    BenchmarkConfig(
        save_dir="evals/step500",
        max_examples=200,
        concurrency=64,
        timeout_seconds=300,
        max_tokens=32768,
        temperature=0.6,
        num_samples=1,
    )
)

# Training-loop integration — evals as reward signals

# BenchmarkEvaluator bridges benchmarks into training loops.
# Returns dict[str, float] metrics at each checkpoint.
# This is the pattern Prime-RL also uses (envs as reward).

What's interesting for Obol

  • Config sensitivity matters. They document that system prompts, max_tokens, temperature, and timeout all shift scores significantly. Obol already captures this in SamplingParams.
  • Evals ↔ training loop. The BenchmarkEvaluator pattern (eval returns dict[str, float] for the training loop to consume) is relevant for Obol's future "eval → routing reward" pipeline.

8. Prime Intellect prime-rl

rl-training

Not an eval harness — it's an RL training framework. But the env/verifier pattern is relevant because Obol's verify step is the same shape.

# Env config (Pydantic) — from prime-rl-configs

class EnvConfig(BaseConfig):
    id: str = "reverse-text"
    name: str | None = None
    args: dict = {}                     # forwarded to vf.load_environment
    num_workers: int | Literal["auto"] = "auto"
    ratio: float | None = None          # sampling weight across envs
    max_total_completion_tokens: int = -1
    timeout: float | None = None
    state_columns: list[str] = []

# TOML config — training run with eval envs

[[orchestrator.train.env]]
id = "math-env"
name = "deepscaler"
args = {
    dataset_name = "agentica-org/DeepScaleR-Preview-Dataset",
    question_key = "problem",
    answer_key = "solution",
    math_verify_max_workers = 128
}

The pattern

Environment (from the verifiers library) is the same shape as Obol's verify function: take agent output, return a reward signal. The orchestrator distributes rollouts across ZMQ workers. The config is TOML with typed Pydantic models — stricter than YAML, less flexible than Python.

9. Prime Intellect verifiers

rl-native framework

The actual eval/reward library underneath prime-rl. This is the most ambitious framework in the survey — it's trying to unify eval and RL reward into one abstraction. 1400-line Environment base class. They're also doing a v1 rewrite.

# Core abstraction: Environment
# verifiers/envs/environment.py — 1400 lines

class Environment(ABC):
    def __init__(
        self,
        dataset: Dataset | DatasetBuilder | None,
        eval_dataset: Dataset | DatasetBuilder | None,
        system_prompt: str | None,
        parser: Parser | None,
        rubric: Rubric | None,            # scoring logic
        sampling_args: SamplingArgs | None,
        tool_defs: list[Tool] | None,
        max_workers: int = 512,
        score_rollouts: bool = True,
        pass_threshold: float = 0.5,
    ): ...

    @abstractmethod
    async def rollout(
        self,
        input: RolloutInput,
        client: Client,
        model: str,
        sampling_args: SamplingArgs | None,
    ) -> State: ...

    async def evaluate(
        self,
        client: Client | ClientConfig,
        model: str,
        num_examples: int = -1,
        rollouts_per_example: int = 1,
        max_concurrent: int = -1,
        results_path: Path | None = None,
        save_results: bool = False,
    ) -> GenerateOutputs: ...

# State — mutable dict with typed fields
# The rollout accumulates state as it goes

class State(dict):
    INPUT_FIELDS = ["prompt", "answer", "info", "example_id"]

    input: RolloutInput
    client: Client
    model: str
    trajectory: list[TrajectoryStep]
    completion: Messages | None
    reward: float | None
    metrics: dict[str, float] | None
    timing: RolloutTiming | None
    error: Error | None
    is_completed: bool
    is_truncated: bool
    stop_condition: str | None

# Rubric — scoring as composable reward functions

class Rubric:
    """Each reward function takes (prompt, completion, answer, **kwargs) -> float"""

    def add_reward_func(self, func: RewardFunc, weight: float = 1.0): ...
    def add_metric(self, func: RewardFunc, weight: float = 0.0): ...
    # weight=0 means tracked but doesn't affect reward — same as Obol's Metric

# RolloutOutput — what comes back from a rollout

class RolloutOutput(dict):
    example_id: int
    prompt: Messages | None
    completion: Messages | None
    reward: float
    timing: RolloutTiming
    is_completed: bool
    is_truncated: bool
    metrics: dict[str, float]
    error: ErrorData | None
    token_usage: TokenUsage

# GenerateOutputs — the final result
class GenerateOutputs(TypedDict):
    outputs: list[RolloutOutput]
    metadata: GenerateMetadata   # env_id, model, avg_reward, pass@k, cost, timing

# Harbor taskset — sandboxed coding tasks (same tasks Obol uses)

class HarborTaskSet(SandboxTaskSet):
    def __init__(self, task_dir: str | Path): ...
    def get_sandbox_spec(self, info: dict) -> SandboxSpec: ...

class HarborRubric(vf.Rubric):
    async def solved(self, state, info, **kwargs) -> float:
        # runs tests in sandbox, parses output, returns 0.0 or 1.0
        test_output = await self.taskset._run_tests(sandbox_client, sandbox_id, state, timeout)
        return float(self.taskset._calculate_reward(test_output, info))

# EvalConfig — Pydantic config for eval runs

class EvalConfig(BaseModel):
    env_id: str
    env_args: dict
    model: str
    client_config: ClientConfig
    sampling_args: SamplingArgs
    num_examples: int
    rollouts_per_example: int
    max_concurrent: int
    save_results: bool = False
    output_dir: str | None = None

class EvalRunConfig(BaseModel):
    evals: list[EvalConfig]       # multiple envs in one run

# ZMQ server — environments run as distributed workers
# env.start_server() spawns a ZMQ process; rollouts go over the wire
# This is for RL training: 1000s of rollouts per second across many workers

await env.start_server(num_workers=8)
# Now env.run_rollout() goes over ZMQ to a worker pool
# Each worker has its own Environment instance

What's good

  • Unified eval + RL reward. Environment.evaluate() for benchmarking, Environment.run_rollout() for training. Same code, same scoring.
  • Rubric composition. add_reward_func(fn, weight=1.0) and add_metric(fn, weight=0.0) — tracked metrics vs reward signals. Same distinction as Obol's Metric(weight=0).
  • ZMQ server mode. Environments can run as distributed workers for RL. If Obol ever feeds rewards into training, this is the shape.
  • Resume support. results_path enables resuming interrupted eval runs by loading existing outputs and filtering remaining inputs.
  • Timing breakdown. RolloutTiming with setup/generation/scoring/model/env phases — more granular than Obol's current timing.

What's concerning

  • 1400-line base class. Environment does too much — dataset management, client resolution, server lifecycle, rollout execution, result saving. Casey would say this needs decomposition.
  • Mutable State dict. State(dict) with typed fields that are actually just dict keys — you get type annotations in the class but no enforcement. The v1 rewrite adds _set_internal() guards but it's still fundamentally a mutable bag.
  • **kwargs everywhere. Environment.__init__ ends with for key, value in kwargs.items(): setattr(self, key, value). Explicitly against Obol's "explicit fields over **kwargs" norm.
  • Granularity issues. You can't use Rubric without Environment. You can't use the scoring without the rollout machinery. The layers are coupled.
The key insight for Obol: verifiers proves the eval↔RL-reward unification works (same Environment, same Rubric). But the implementation couples too many concerns. Obol's separation of TaskSpec.verify (scoring) from TaskSpec.runtime (agent execution) is cleaner — keep it. If you need the RL bridge later, it's verify → reward signal, not a rewrite.

10. OpenAI Evals REST API (hosted, deprecated Nov 2026)

hosted deprecated

The only hosted REST API in the survey. Shows what the "fully productized" shape looks like. Being deprecated — instructive about what not to build too early.

# Create an eval
POST /v1/evals
{
  "name": "my-qa-eval",
  "data_source_config": {
    "type": "custom",
    "item_schema": {
      "type": "object",
      "properties": {
        "question": {"type": "string"},
        "expected": {"type": "string"}
      }
    }
  },
  "testing_criteria": [
    {
      "type": "string_check",
      "input": "{{sample.output}}",
      "operation": "eq",
      "reference": "{{item.expected}}"
    }
  ]
}

# Submit a run
POST /v1/evals/{eval_id}/runs
{
  "data_source": {
    "type": "responses",
    "model": "gpt-5.5",
    "input_messages": {
      "type": "template",
      "template": [
        {"role": "user", "content": "{{item.question}}"}
      ]
    },
    "source": {"type": "file_id", "id": "file-abc123"}
  }
}

# Get results
GET /v1/evals/{eval_id}/runs/{run_id}
→ { result_counts, per_testing_criteria_results, token_usage, status }

Why it's being deprecated

  • No escape hatch. You can't run evals locally. If the API goes down, you're stuck.
  • Template-only. Complex scoring logic doesn't fit in testing_criteria JSON.
  • Granularity hole. You can use the full hosted API or nothing. No intermediate layer for "I want to define the eval in code but submit it remotely."
Lesson: Going straight to hosted REST API without a solid local-first foundation is a mistake. OpenAI built the product layer before the framework layer was mature, and now they're shutting it down.

12. Where Obol Sits & What to Steal

Obol is currently at the simple-evals/Inspect boundary: Python config modules, frozen dataclasses, direct CLI execution. The wide events and fingerprinting already go beyond what most harnesses have. The multi-runtime/multi-endpoint architecture is unique — none of the others support "run the same task through Pi, Codex, and Claude Code."

The path forward: layers, not rewrites

Casey's granularity rule: each new layer must be trivially replaceable by the layer below it. bool_button on top of push_button on top of raw UI calls.

Layer 0: RunSpec (exists)

keep as-is

Frozen, serializable, fully determines a run. This is the protocol. Equivalent to simple-evals' Eval.__call__ contract.

RunSpec(
    run_id, endpoints, workloads, output_dir, max_concurrent, skip_indices
)

Don't touch this. Everything else builds on top.

Layer 1: Experiment Registry (steal from nmoe + openai-evals)

next step

SQLite table tracking runs. Like nmoe's experiment registry, but simpler. Like openai-evals' RunSpec + Event recorder.

# Schema
CREATE TABLE runs (
    run_id        TEXT PRIMARY KEY,
    config_hash   TEXT NOT NULL,
    config_json   TEXT NOT NULL,       # serialized RunSpec
    git_sha       TEXT NOT NULL,
    git_dirty     BOOLEAN NOT NULL,
    config_module TEXT,
    status        TEXT NOT NULL,       # pending | running | ok | partial | failed
    started_at    TEXT,
    ended_at      TEXT,
    summary_json  TEXT,                # serialized WorkloadSummary
    host          TEXT,                # laptop | proxy
);

# CLI usage (new commands, existing binary)
$ obol runs ls
$ obol runs ls --status ok --model "Qwen*"
$ obol runs show sweep_tb21_pi.kimi-k2.6
$ obol runs compare run_a run_b

This is useful immediately — locally, before any remote execution. It gives you "what ran, with what config, from what commit" without grep.

Layer 2: Remote Submission (steal from Braintrust's simplicity)

future

The thinnest possible HTTP wrapper. Not a new service architecture — just "accept a RunSpec over HTTP, spawn the same CLI, tail the events."

# Submit (from laptop)
$ obol submit --config obol.configs.sweep.baseline_tb21 --host proxy
# → Serializes RunSpec, POSTs to proxy, returns run_id
# → proxy: python -m obol --config-json '...' (new flag)

# Or programmatic
POST http://proxy:8080/runs
Content-Type: application/json
{ "config_module": "obol.configs.sweep.baseline_tb21" }
→ { "run_id": "sweep_tb21_pi.kimi-k2.6_a1b2c3d4", "status": "pending" }

# Status (same registry, exposed over HTTP)
GET http://proxy:8080/runs/{run_id}
→ { "status": "running", "summary": {...}, "events_url": "/runs/{id}/events" }

# Stream events (SSE or JSONL — the wide_events.jsonl already exists)
GET http://proxy:8080/runs/{run_id}/events
→ streaming JSONL (same format as the file)

Key: obol submit is bool_button — it calls push_button (obol --config X) under the hood. You can always drop down to SSH + tmux.

Layer 3: Comparison & Dashboard (steal from Braintrust + Inspect)

later

Braintrust's baseExperimentName is the killer feature: "show me what changed." Inspect's viewer is the reference for local results inspection. Both are powered by the data Obol already collects (wide events + summaries).

# Compare runs (CLI)
$ obol runs compare sweep_v1 sweep_v2
┌────────────────────┬──────────┬──────────┬────────┐

What NOT to steal

  • YAML configs (lm-eval). Python modules are strictly more powerful, and Obol's configs are already clean. YAML adds a parser/validator layer for no gain when your users are you.
  • Hosted-first API (OpenAI Evals API). They built the REST API before the local framework was solid, and it's being deprecated. Local-first, remote-later.
  • TypeScript (Braintrust). The Eval(name, {data, task, scores}) shape is great; the language choice is not relevant.
  • Complex solver composition (Inspect). Obol's runtimes (Pi, Codex, CC) are already more flexible than Inspect's solver chains. Don't add a solver registry.

Immediate sequencing recommendation

  1. Experiment registry (SQLite) — useful today, locally. obol runs ls/show/compare.
  2. RunSpec JSON serialization — --config-json flag so the proxy can receive a spec without importing Python modules.
  3. Clone obol to proxy box — uv sync, tmux, run sweeps. No HTTP layer needed yet.
  4. Thin HTTP wrapper — when "SSH and tmux" becomes annoying. Not before.
Sean Goedecke's system design principle applies: "good design looks like nothing going wrong for a long time." The experiment registry is the one piece that's genuinely missing. Everything else — remote submission, dashboards, comparison — can be built on top of it when the pain is real.
