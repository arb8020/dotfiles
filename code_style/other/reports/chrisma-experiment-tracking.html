Experiment tracking & durable execution — build vs buy analysis

Tracking Durable exec Orchestration Infrastructure

Recommendation

Use obol/ledger. It solves both problems in one library with zero infrastructure.

Ledger is the only option that provides experiment tracking and durable execution as a single primitive. It runs on SQLite (no server), speaks the same patterns chrisma already uses (append-only logs, idempotent sweeps), and lives in the same org. MLflow/W&B give tracking without durability; Temporal/Absurd give durability without tracking. Ledger gives both with pip install.

Problem: chrisma has no structured experiment store and no checkpoint/resume below problem level.

Solution: Ledger's step(key, fn) caches completed work per run identity; log()/metric() write to a queryable SQLite projection backed by an append-only JSONL event stream.

Wins

Tracking + durability in one library

Zero infrastructure (SQLite)

step() maps to iteration loop

Same org, same maintainers

Event-sourced, projections rebuildable

Contract-tested API (frozen at v1)

Costs

v0 — API not frozen yet

No comparison UI

Not extracted to own package

Lease scanning unresolved

# kb-agent worker loop (after)
import obol.ledger as ledger

lg = ledger.open("runs/chrisma.db")
with lg.run(f"kb-{tag}-{problem}", config=sweep_cfg, tags=[f"sweep:{tag}"]):
    for i in range(max_iters):
        kernel = ledger.step(f"iter-{i}-gen", lambda: glm_generate(problem, history))
        result = ledger.step(f"iter-{i}-bench", lambda: benchmark(kernel))
        ledger.log({"speedup": result.speedup, "status": result.status}, step=i)
        if result.is_winner:
            ledger.artifact("winner", path=str(kernel_path))
            ledger.summary({"best_speedup": result.speedup})
# Worker dies at iter 7 → restart → iters 0-6 replay from cache → resumes at 7

Adjacent art: noumena-network/nmoe

nmoe's experiment system — patterns worth borrowing

nmoe independently built a similar stack: SQLite-backed ExperimentTracker, DuckDB+Parquet metrics, TOML-driven campaign orchestration with coordinate descent search. Key patterns:

TOML campaign specs → chrisma sweep configs

Git-aware runs (hash + dirty state)

Claim system for improvements over baselines

Leaderboard auto-append from run results

These are orchestration-layer patterns. They compose on top of ledger's tracking primitives. Consider porting nmoe's campaign TOML format for chrisma's sweep definitions.

ADR: experiment tracking backend

Decision: Use obol/ledger for experiment tracking and durable execution in chrisma-new.

Context: chrisma-new needs structured run tracking and checkpoint/resume for GPU workers. The system runs on bare-metal GPU nodes with no cloud services or PostgreSQL.

Alternatives rejected:

  • MLflow/W&B: no durable execution, requires server infrastructure or SaaS
  • Temporal: massive overkill for 2-3 GPU node workers, heavy infra
  • Absurd: solves durability but requires PostgreSQL + separate tracking system
  • Custom SQLite: would duplicate what ledger already built and tested

Consequences: chrisma-new becomes ledger's first external consumer, which freezes the tracking API to v1 per ledger's roadmap. Ledger needs to be importable without pulling all of obol.
